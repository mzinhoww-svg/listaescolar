# S07 · Upload e OCR síncrono de 10 s com fallback · Plano de implementação (trilha Pipeline, índice 2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Upload de foto ou PDF de lista para bucket privado, com limite de tamanho e tipo e consentimento registrado em `consents`; Server Action com orçamento de 10 s para o pipeline de extração; se estourar, enfileira em pgmq e devolve `job_id` (`processing_async`); a tela mostra "continuar aguardando", ativar notificação e canal opcional; worker em Edge Function, idempotente, com retry exponencial e dead letter; status persistido e consultável.

**Architecture:** Núcleo em TypeScript puro e testável: `features/submissions/` (serviço de envio com orçamento de tempo, portas `ExtractionPipeline`, `SubmissionStore`, `JobQueue`, `Clock`) e `supabase/functions/_shared/worker-core.ts` (worker sem APIs do Deno, importável pelo Vitest). Banco: `consents`, `list_submissions`, `jobs`, `ocr_jobs`, extensão `pgmq` com filas `ocr_jobs` e `ocr_jobs_dlq`, bucket `list-uploads` privado. O extrator real (IA) chega na S08: aqui só a porta e um pipeline de demonstração atrás de flag. **Sem FK para tabelas de outras trilhas** (ADR-004): `school_id` e `grade`/`school_year` são colunas sem FK; a publicação/versão de lista é a porta `ListPublisher` da S09/S11.

**Tech Stack:** Next.js 16 (Server Actions, Route Handlers), Supabase (Storage, pgmq, Edge Functions/Deno), Zod, `unpdf` (só se precisar contar páginas/extrair texto; server-only), Vitest, agent-browser. Worktree `../listaescolar-wt/T2-pipeline`, trilha 2 (`.track` = 2): `pnpm db:start`, `pnpm db:env`, app em `PORT=3002`.

**Spec:** `docs/SPEC.md` §4 (job_status, list_status), §5 (Envios e processamento, consents), §6 (OCR), §8; `docs/PLAN.md` S07; `docs/decisions/ADR-004-trilhas-paralelas.md`. Telas (mobile 390×844; leia PNG e HTML): `App06-Foto`, `App15-EnviarLista`, `App20-AILoading`; desktop 1280×800: `Escola08-UploadPDF`.

## Global Constraints
- Migration `supabase/migrations/0201_submissions_and_jobs.sql` (faixa Pipeline 02xx). Toda tabela: `id uuid primary key default gen_random_uuid()`, `created_at`, `updated_at` (trigger `set_updated_at`), RLS habilitada. FK só para `auth.users`/`profiles`/`municipalities` e tabelas desta trilha.
- Tabelas: `consents` (`profile_id`, `purpose text`, `text_version text`, `granted_at`, `revoked_at`); `list_submissions` (`submitted_by` → profiles, `source` enum `submission_source` (`parent`, `school`), `school_id uuid` sem FK, `grade text`, `school_year int`, `storage_path`, `file_name`, `mime_type`, `size_bytes`, `consent_id` → consents, `status list_status` default `submitted`, `is_demo boolean`); `jobs` (`kind text`, `payload jsonb`, `status job_status` default `queued`, `attempts int`, `max_attempts int default 5`, `last_error text`, `run_after timestamptz`, `idempotency_key text unique`, `notify_channel` enum `notify_channel` (`none`, `browser`, `email`, `whatsapp`) default `none`, `notify_target text`, `submission_id uuid`); `ocr_jobs` (`job_id` → jobs, `submission_id` → list_submissions, `result jsonb`, `duration_ms int`).
- Estados são os enums do spec: `list_status` (`submitted`, `processing`, `processing_async`, `review_needed`, `human_review`, `approved`, `published`, `archived`, `rejected`, `draft`) e `job_status` (`queued`, `running`, `succeeded`, `failed`, `retrying`, `dead`). A S07 só usa `submitted`, `processing`, `processing_async`, `review_needed` (resultado pronto) e `rejected`/`failed` para erro.
- Storage: bucket privado `list-uploads` (10 MB por arquivo; tipos `application/pdf`, `image/jpeg`, `image/png`, `image/webp`, `image/heic`); caminho `{profile_id}/{submission_id}/{arquivo}`; políticas: usuário autenticado insere/lê só a própria pasta; admin lê tudo; anon nada. Validação de tipo por assinatura de bytes (magic bytes), não só pelo `Content-Type`.
- **Consentimento antes do upload:** o envio só ocorre com consentimento explícito (`purpose = 'list_upload'`, `text_version` fixo em constante versionada); grava `consents` e referencia em `list_submissions`. Sem consentimento → erro de validação e nada é gravado. Texto do consentimento apenas o que a tela App15 traz.
- **Orçamento de 10 s:** constante `SYNC_BUDGET_MS = 10_000` injetável (`Clock`/timeout) para testes. Se o pipeline concluir dentro do orçamento → status `review_needed` com `ExtractionResult`; se estourar (timeout) → enfileira (`jobs` + `pgmq.send('ocr_jobs', {job_id})`), status `processing_async`, devolve `job_id`. O trabalho do pipeline que estourou é cancelado (`AbortSignal`) ou tem o resultado descartado; **nunca** dois resultados para o mesmo envio (idempotência por `idempotency_key = submission_id`).
- **Worker:** consome `ocr_jobs` de forma idempotente por `job_id` (job já `succeeded` é ignorado; `running` recente é ignorado; mensagem duplicada não reprocessa), retry exponencial com jitter limitado (base 30 s, fator 2, teto 15 min) ajustando o visibility timeout do pgmq, após `max_attempts` move para `ocr_jobs_dlq` e marca `jobs.status = 'dead'` e `list_submissions.status` coerente; `jobs.attempts` e `last_error` (sem dado pessoal, truncado) persistidos. Status consultável por `GET /api/submissions/[id]/status` (dono ou admin) devolvendo `{status, jobStatus, attempts, result?}`.
- **Porta `ExtractionPipeline`** (`extract(input, { signal }) → Promise<ExtractionResult>`): a S08 fornece a implementação real. `ExtractionResult` (Zod) mínimo: `{ items: { name: string; quantity: number | null; unit: string | null; confidence: number }[]; overallConfidence: number; warnings: string[] }`. Pipeline de demonstração (`DemoExtractionPipeline`, modos rápido/lento/falha) só habilita com `DEMO_PIPELINE=1` e **nunca em produção** (`NODE_ENV=production` sem a flag explícita `ALLOW_DEMO_IN_PRODUCTION` = erro de boot na validação de env). Sem pipeline configurado, o envio grava o arquivo, o consentimento e enfileira, e a tela informa "leitura automática indisponível no momento" (nunca inventar itens).
- Notificação/canal: no estado assíncrono a tela oferece "continuar aguardando", "ativar notificação do navegador" (apenas registra `notify_channel = 'browser'`; o Web Push real é da S11) e informar e-mail ou WhatsApp (valida com Zod, grava em `jobs.notify_target`, visível só ao dono e admin). Nenhum dado de menor em nenhum campo.
- Segurança: Server Action exige login (`parent`, `school_member`, `admin`; nunca metadata), limite de tamanho aplicado ANTES de ler tudo em memória, nome de arquivo sanitizado, tipo por assinatura, Zod em toda fronteira. Service role só em código de servidor (`server-only`) e no worker. Componentes ≤250 linhas; `"use client"` só com interação. TypeScript strict, sem `any`.
- Ledger: Rulings desta trilha em `docs/superpowers/ledger-pipeline.md`.

## Review Focus
- Estouro do orçamento no meio da extração: não pode gerar resultado duplicado nem deixar `list_submissions` em `processing` para sempre; reenvio do mesmo arquivo cria envio novo (não reaproveita) mas nunca duplica job do mesmo envio.
- Arquivo com `Content-Type` mentiroso (exe renomeado para `.pdf`), 0 bytes, > 10 MB, PDF criptografado/corrompido, imagem gigante, nome com `../` ou caracteres de controle, upload sem consentimento, upload por usuário sem login.
- Worker: mensagem duplicada; job removido; falha permanente → DLQ e `dead`; falha transitória → retry com backoff (teste com relógio falso); crash após processar e antes de confirmar a mensagem (não reprocessa efeito colateral); concorrência de dois workers na mesma mensagem.
- RLS: usuário A não lê envios, jobs nem arquivos do usuário B; `notify_target` invisível a terceiros; anon nada; o bucket não serve URL pública.
- Status consultável: usuário não vê status de envio alheio (404, não 403 revelando existência).
