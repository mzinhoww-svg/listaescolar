## Rulings de escopo (registrados aqui e no ledger antes de codar)
1. **Migration na faixa `06xx`.** `0604_admin_reports.sql` já existe na branch paralela `slice/S16-admin` (T3,
   conferido via `git ls-remote`/worktree). Esta fatia usa **`0605_lgpd_privacy.sql`**. Se colidir no merge com a
   S16 (pouco provável, prefixos diferentes), renumerar esta.
2. **`claims.claimant_id` e `claim_evidence.uploaded_by` passam de `on delete restrict` para `on delete set null`
   (e ficam nullable).** É o único jeito de a exclusão de conta apagar `profiles`/`auth.users` de verdade quando o
   dono tem histórico de reivindicação — sem isso, `DELETE` trava com FK violation e a exclusão "real" do perfil
   fica impossível para qualquer reivindicante. O registro da reivindicação (decisão, escola, datas) é o
   livro-razão que precisa ficar (evidência de quem verificou a escola); o campo pessoal (nome, cargo, e-mail,
   nota) é anonimizado por um novo gatilho `profiles_lgpd_erase` (BEFORE DELETE em `profiles`) antes do `SET NULL`
   surtir efeito. Custo se errado: reverter para `restrict` é aditivo (mais uma migration), mas qualquer conta já
   excluída com reivindicação já teria sido apagada — o Ruling vale a partir de quando for aplicado.
3. **`profiles_lgpd_erase` (gatilho BEFORE DELETE em `profiles`, SECURITY DEFINER, `search_path=''`, `enable
   always`) concentra a anonimização que nenhuma FK alcança:** `claims` (nome, e-mail, nota) para linhas onde
   `claimant_id = old.id`; `claim_evidence.original_name` (nome do arquivo pode conter PII) para linhas onde
   `uploaded_by = old.id`; `lead_events.actor_id` (D-014, sem FK) para `null`. Rodar como gatilho (não só numa
   função de "excluir conta" chamada pelo app) garante que a anonimização acontece mesmo que o perfil seja
   removido por outro caminho (admin API do Supabase Auth cascade). Custo se errado: gatilho aditivo, sem
   migração de dado histórico (não há dado de produção).
4. **Tabelas "livro-razão" que ficam (não apagam, e já não têm dado pessoal identificável depois do Ruling 2/3):**
   `leads` (requester_id → null via FK já existente), `lead_events` (actor_id → null via gatilho), `lead_conversions`/
   `sale_declarations` (actor_id → null via FK já existente), `invoices`/`credit_ledger` (actor_id já sem FK, nunca
   foi de responsável e sim de admin/system — não é dado pessoal do titular da conta), `claims`/`claim_evidence`
   (anonimizados pelo Ruling 3, mantidos como registro de decisão), `audit_log` (já não guarda PII em claro para
   nenhuma tabela auditada; append-only, sem exclusão nesta fatia — o PLAN só pede job de exclusão de
   "documentos vencidos", não de `audit_log`).
5. **`retention_policies` cobre exatamente o gap de D-012 nesta fatia: `claim_evidence` (documento pessoal,
   `retention_days` contados de `claims.decided_at`, só claims em estado final) e `claim_tokens` (hash, sem PII,
   `retention_days` contados de `expires_at`, higiene/D-012).** Os valores de `retention_days` são um padrão
   técnico provisório (180 e 90 dias), guardados numa tabela editável pelo `service_role`/futuro admin — não são
   fato jurídico inventado (CLAUDE.md proíbe inventar preço/prazo/métrica do PRODUTO; isto é parâmetro de
   engenharia, documentado como provisório, igual ao próprio placeholder da página de privacidade). Estender a
   outros recursos (ex.: documentos de `list_submissions`) fica para dívida nova, fora do escopo de D-012.
6. **Exclusão de conta é uma função só (`account_delete_request`, SECURITY DEFINER, EXECUTE só `service_role`),
   chamada pelo Server Action com `p_profile_id = auth.uid()` da sessão (mesmo padrão de `consents_revoke`).**
   Ela apaga primeiro os documentos do Storage do próprio dono (chamado pelo Server Action ANTES do DELETE do
   `auth.users`, com a lista de `storage_path` de `list_submissions`/`claim_evidence` do dono, best-effort) e só
   depois chama `auth.admin.deleteUser` (cascade cuida do resto pelas FKs). Falha ao apagar Storage não bloqueia a
   exclusão do banco (best-effort, registrado em log; D-017 já documenta esse padrão para claim-evidence).
7. **Exportação (`account_export`) é SECURITY DEFINER mas só lê dados do PRÓPRIO `auth.uid()` (sem parâmetro de
   profile_id — impossível pedir o de outra pessoa), devolvendo um `jsonb` por seção (perfil, consentimentos,
   estudantes, listas salvas, carrinhos, cotações como solicitante, reivindicações como reivindicante, assinaturas
   push, preferências de notificação, envios de lista).** Nunca inclui dado de terceiro (papelaria, outro
   responsável) nem o conteúdo de arquivos (só metadados: nome, caminho, tipo, tamanho — o app pode gerar link
   assinado por fora se quiser, fora do escopo desta fatia).
8. **Selo "Demonstração":** `DemoBadge` já é usado amplamente; a Task 4 faz uma auditoria dirigida (grep de toda
   consulta que expõe `is_demo` para a UI) e corrige só as lacunas encontradas, com teste cobrindo cada correção.
   Não reconstruir o componente.
9. **D-015 e D-016 (dono S17, severidade média/baixa) ficam registrados como decisão explícita, não corrigidos
   nesta fatia:** D-015 (texto do lead não cita bairro/evento visível à papelaria) é comércio/UX de outra
   tabela (`leads`), não é um gap de LGPD estrutural (o dado já é mostrado ao consentir, só falta o texto ser mais
   explícito) — vira dívida rebaixada com nota; D-016 (aceite de reivindicação em `claims.privacy_ack_at`, não em
   `consents`) tem custo de mudança de fluxo de outra fatia (S06) e nenhum requisito do PLAN pede migrar isso —
   mantido `aberta` com Ruling de que não bloqueia LGPD (o timestamp e a versão do texto já existem, só não estão
   na tabela central).

## Global Constraints
- TypeScript strict, sem `any`; Zod em toda fronteira (Server Actions e schemas).
- Componente React ≤ 250 linhas; Server Components por padrão; `"use client"` só com interação.
- Migration `0605_lgpd_privacy.sql`: uuid/`created_at`/`updated_at` em toda tabela nova, RLS em toda tabela nova,
  `SECURITY DEFINER` com `search_path=''` e `EXECUTE` revogado de `public/anon/authenticated` (e de `service_role`
  quando a função só é gatilho) em TODA função nova, com teste de `has_function_privilege`; grants por coluna
  onde há UPDATE; gatilhos `enable always`.
- Job de retenção: idempotente, teto por execução, nunca toca `survey_*` (ADR-005 — teste cobre isso
  explicitamente), segredo de cron em tempo constante (mesmo padrão de `isAuthorizedCron`/`CRON_SECRET_MIN_LENGTH`
  de `features/leads/cron-auth.ts`, reaproveitado).
- Exportação só do próprio usuário; exclusão real do que é pessoal, anonimização do que é livro-razão, sem quebrar
  imutabilidade (`audit_log`, `claim_status_events`, `lead_events`, `b2b_*_ledger` continuam append-only).
- Nada de afirmar conformidade jurídica; menores só apelido e série (nenhuma mudança nisso).

## Review Focus
- `claims.claimant_id`/`claim_evidence.uploaded_by`: agora nullable, `on delete set null`; `profiles_lgpd_erase`
  anonimiza ANTES do `SET NULL` valer (mesma transação, BEFORE DELETE); teste cobre reivindicação aprovada
  sobrevivendo (escola continua `verified`) com campos pessoais irreconhecíveis.
- `retention_run`: nunca deleta linha de `survey_responses`/`survey_leads` (teste explícito com contagem antes e
  depois), respeita teto por execução, idempotente (rodar duas vezes não falha nem duplica exclusão).
- `account_export`: só devolve dados de `auth.uid()`; teste cria dois `parent` e confere que um nunca vê dado do
  outro nem de papelaria/escola.
- `account_delete_request`: teste cobre dono com reivindicação aprovada (perfil apaga de verdade, `claims`
  sobrevive anonimizada, escola continua `verified`) e dono sem reivindicação (tudo cascade, nada sobra ligado ao
  perfil exceto os `on delete set null` já existentes).
- `has_function_privilege` falso para `anon`/`authenticated` em toda função nova exceto as que o app chama pela
  sessão (nenhuma nesta fatia — todas passam por `service_role`, mesmo padrão de `consents_revoke`).
