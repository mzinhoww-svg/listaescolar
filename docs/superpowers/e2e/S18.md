# E2E · S18 Estados e acessibilidade

Build de produção local (`pnpm build && PORT=3003 pnpm start`), worktree `T3-comercio`, banco local
(`supabase_db_listacerta-t3`), roteiro `scripts/e2e-s18.sh` (agent-browser), reaproveitando
`scripts/e2e-lib.sh` (D-091, extraído nesta fatia). Sessões `t3s18-<run>-admin`/`-visit`. Fixture: uma escola,
lista publicada com 4 itens (2 em "Papelaria", 1 em "Higiene", 1 sem categoria) e uma denúncia `open` sobre essa
lista, inseridos por SQL direto antes do roteiro.

**Resultado final: 18 PASS, 0 FAIL.**

Duas rodadas intermediárias tiveram falhas reais de ROTEIRO (não de produto), ambas corrigidas antes da rodada
final:
- Comparação de texto sensível a maiúsculas contra um `<h3 className="uppercase">` (CSS `text-transform`; o texto
  gravado é `higiene`/o grupo sem categoria vira `Outros itens`, mas `get text body` do agent-browser captura o
  texto RENDERIZADO — `HIGIENE`/`OUTROS ITENS`). Corrigido em `scripts/e2e-lib.sh`: `has`/`wait_text` passam a
  comparar sem diferenciar maiúsculas (comentário no próprio arquivo registra o achado).
- O passo de D-153 reabria a MESMA URL (`ab admin open` duas vezes para `/admin/denuncias/[id]`) esperando ver o
  `<select>` de resolução habilitado depois de mudar o status para `reviewing` — mas reabrir a URL idêntica é um
  no-op (o navegador/roteador não refaz a navegação), então a releitura via `eval` ainda via o DOM de antes do
  clique. A falha foi confirmada como só de roteiro checando direto no banco (`select status from reports` já
  mostrava `reviewing`) e com uma sessão nova, isolada, confirmando `disabled === false` logo após um login/
  abertura genuína da mesma página. Corrigido trocando a releitura por `location.reload()` (força um GET de
  verdade) em vez de reabrir a mesma URL — candidato a lição para o PAT-002 do Segundo Cérebro (mesma classe de
  achado de "wait_text"/checkbox de sessões anteriores: reabrir a MESMA URL não é reload).

## Cenários

1. **D-034 + D-140 (lista oficial pública, `/escolas/[inep]/[serie]`)**: itens agrupados por categoria
   ("Papelaria", "Higiene", "Outros itens" por último, para o item sem categoria); link "Montar carrinho com
   esta lista" presente e apontando para `/carrinho/novo?lista=<id da versão publicada>` (não o id da lista).
2. **Foco visível/skip-link por teclado (`AdminShell`, novo nesta fatia)**: primeiro elemento focável ao entrar
   em `/admin` é o skip-link ("Pular para o conteúdo"), com `href="#conteudo"`; `main#conteudo` existe na casca.
3. **D-153 (`/admin/denuncias/[id]`)**: com a denúncia `open`, o `<select name=resolution>` e o botão "Resolver"
   ficam desabilitados (só "Colocar em análise" é uma transição válida); depois do clique em "Colocar em
   análise" (status vira `reviewing`), os mesmos campos ficam habilitados.
4. **Verificador axe-core** (via CDN `cdnjs.cloudflare.com/ajax/libs/axe-core`, sem dependência nova no
   projeto) em 3 rotas representativas: a lista pública, o dashboard do admin e o detalhe de uma denúncia —
   nenhuma violação de impacto `serious`/`critical` em nenhuma das três.
5. **Site público (`/`)**: skip-link como primeiro elemento focável, 8 Tabs seguidos todos com indicador de foco
   visível, `h1`/`main` únicos, nenhuma `<img>` sem `alt`, nenhum link/botão sem nome acessível (verificado numa
   rodada suplementar, ver seção seguinte).

## Cobertura fora deste roteiro

Os demais itens de D-057 (refatoração pura, sem UI) e das dívidas resolvidas por texto/lógica sem componente
visual novo (D-029, D-038, D-080, D-083, D-084, D-090, D-091, D-092) são cobertos pelos testes automatizados
(unitários e de banco, ver commits desta fatia), não repetidos aqui por não terem uma tela própria a visitar ou
já estarem cobertos por roteiros de fatias anteriores (ex.: `PushOptIn`/D-080 é testado por
`tests/notifications/central/components.test.tsx` com mocks de `pushManager`, que exercitam o navegador real
melhor do que um roteiro de agent-browser conseguiria sem hardware de push de verdade).

`PanelShell` (papelaria), `PortalShell` (B2B) e `SchoolShell` (escola): sem conta de demonstração seedada por
padrão para esses três papéis nesta sessão; a cobertura de skip-link/`main#conteudo`/foco visível para as três
cascas vem de `tests/a11y/shells.test.tsx` (unidade), não de uma sessão de navegador real — mesmo padrão do
`AdminShell` (item 2), só que confirmado ao vivo para este último. Estado de "carregamento" (`app/loading.tsx`)
durante streaming não é observável de forma confiável por um roteiro síncrono (a resposta HTTP já chega completa
quando o roteiro lê o corpo); cobertura vem de `tests/a11y/loading-and-buttons.test.tsx`.

## Achado operacional (não é bug de produto): rodada suplementar com esgotamento de Chrome/agent-browser

Depois da rodada final (18/0), uma verificação suplementar (nova sessão, porta 3013) tentou reconfirmar o item 5
(site público) e reexecutar os itens 2–3 numa sessão isolada. O item 5 passou. Os itens 2–3, e uma checagem
adicional de "abrir a home simples", falharam com `net::ERR_CONNECTION_REFUSED` no `agent-browser`/Chrome — no
mesmo instante em que `curl` contra o mesmo servidor respondia 200/307 normalmente. `ps aux` mostrava ~40
processos residuais de `Google Chrome Helper` (das várias rodadas de E2E desta sessão, inclusive uma rodada
concorrente de outro subagente no mesmo worktree — ver o Ruling de concorrência em `ledger.md`/nota em
`PROGRESS.md`). Isolado como esgotamento de recursos do Chrome nesta máquina, não como regressão do produto: os
mesmos itens (2–3) já tinham passado 100% na rodada final documentada acima, com capturas de tela reais
(`S18-02-admin-skiplink.png`, `S18-03-denuncia-open.png`, `S18-04-denuncia-reviewing.png`). Sem matar processos de
terceiros (regra inviolável desta tarefa: nunca `pkill`/`close --all`), a rodada suplementar foi encerrada como
achado documentado, não repetida à força.
