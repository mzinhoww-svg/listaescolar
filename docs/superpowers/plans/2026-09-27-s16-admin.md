# S16 · Admin · Plano de implementação (trilha Comércio, worktree T3, índice 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Dashboard do admin com contagens reais por estado de escola, lista, reivindicação, papelaria e lead
(Admin01-Visao); auditoria filtrável do `audit_log` (Admin08-Eventos); fila de denúncias (`reports`, tabela nova);
edição de `ai_settings` pelo admin (limiares, alertas críticos, `max_escalations`, `pipeline_version`; NUNCA liga
`auto_publish_enabled` nesta fatia); arquivar lista pela máquina de estados já existente (`list_archive`, 0103),
com motivo.

## Levantamento (feito antes deste plano)
- `/admin` (`app/admin/page.tsx`) é hoje um stub sem números. `AdminShell` já lista as seções existentes
  (`components/admin/AdminShell.tsx`); precisa de 3 itens novos de nav (`/admin/eventos`, `/admin/denuncias`,
  `/admin/ia`).
- `/admin/auditoria` (S22) é a auditoria de CONVERSÃO (Admin11), não a auditoria geral (`audit_log`, Admin08) —
  não se sobrepõe; a auditoria geral desta fatia ganha rota nova `/admin/eventos`.
- `audit_log`, `schools`, `school_lists`, `claims`, `stationeries`, `leads` já têm política RLS
  `..._select_admin` (`(select public.auth_role()) in ('admin','system')`) desde S01–S14 — o dashboard e a
  auditoria filtrável leem por essas políticas, com o client de SESSÃO (`lib/supabase/server.ts`), sem função SQL
  nova: menos superfície, mesma garantia (RLS + `getSessionActor` na Server Action/página).
- `ai_settings` já tem RLS `admin`/`system` completa (select/insert/update) e CHECKs de domínio desde 0202 (S08),
  com o comentário `-- edição pelo admin (S16)` no grant de update — esta fatia só constrói a UI e o Zod, sem
  migration para a tabela em si.
- `list_archive(p_list_id, p_actor_id, p_reason)` (0103, S05) e `features/lists/repository.ts#archive()` já existem
  (`published -> archived`, evento em `list_status_events`, `service_role`) — sem uso ainda em nenhuma UI. Esta
  fatia só adiciona a tela/ação do admin que chama o repositório já existente.
- `reports` (denúncias) não existe: tabela nova nesta fatia, faixa pós-trilhas `06xx` (maior atual: `0603`) →
  `0604_admin_reports.sql`.

## Rulings de escopo (registrados aqui e no ledger antes de codar)
1. **Dashboard e auditoria geral sem função SQL nova.** Leitura por RLS existente com o client de sessão; contagem
   por `count: 'exact', head: true` por valor de enum (conjuntos pequenos e fixos), em paralelo. Sem dado ->
   "indisponível" por categoria (falha isolada não derruba o painel inteiro).
2. **`reports`: sem texto livre com dado pessoal.** `reason` é enum; `detail_code`/`resolution_note` são só código
   curto (mesma regex de `ai_decisions.justification`: `^[a-z][a-z0-9_:.-]{0,59}$`), nunca prosa. Sem coluna de
   contato do denunciante (o próprio `reporter_id`, sem FK — padrão `ai_decisions.actor_id`, ADR-004 — já basta para
   o admin agir). `audit_log` não recebe nem IP em claro (só existe `ip_hash`, já hash) nem linha de `students`
   (defesa em profundidade: filtro explícito `entity_table <> 'students'` na leitura, mesmo sem gatilho algum hoje
   escrevendo `students` no `audit_log`).
3. **`ai_settings`: `auto_publish_enabled` fica só leitura nesta fatia.** Ligar sozinho violaria a regra do CLAUDE.md
   ("nunca ligando `auto_publish_enabled` sozinha sem Ruling") e o D-077 (IA bloqueada no staging); a UI mostra o
   valor atual e um aviso, sem campo editável. `routes` (JSON de roteamento de modelo) também fica só leitura (edição
   seria uma segunda fatia — risco de moderar um formulário genérico de JSON heterogêneo sem cobertura de teste
   proporcional ao tempo desta fatia); os campos editáveis são `confidence_threshold`, `item_confidence_threshold`,
   `critical_alerts`, `max_escalations`, `pipeline_version`, todos com CHECK de banco já existente + Zod espelhado.
4. **Arquivar lista: entrada única em `/admin/denuncias/[id]` para o alvo `school_list`, mais busca direta em
   `/admin/listas/[id]`.** Sem índice navegável de todas as listas publicadas (fora do prompt da fatia); o link
   direto por id/rota é suficiente para a ação "arquivar lista com motivo" pedida no PLAN, e a fila de denúncias é
   o caminho natural de descoberta (denúncia de lista errada -> arquivar).
5. **Denúncia pública mínima.** Único ponto de entrada nesta fatia: um formulário curto (motivo por enum) na página
   pública da escola (`app/escolas/[inep]/page.tsx`), só para usuário autenticado (qualquer papel), alvo
   `school_list` da lista publicada em exibição. Denúncia de papelaria/catálogo fica de fora do ponto de entrada
   desta fatia (a tabela já suporta os dois `target_type`; sem tela pública ainda — dívida nova, ver DEBT).
6. **DEBT D-006, D-007, D-035, D-036, D-037, D-083 (donos S16):** nenhum é o prompt central desta fatia
   (dashboard/auditoria/denúncias/`ai_settings`/arquivar). Decisão por item, registrada no ledger e no DEBT.md ao
   final: D-006 (confirmação antes de aprovar reivindicação) é pequena e de UX direta — corrigida nesta fatia junto
   da Task 2, sem migration. D-007, D-035, D-036, D-037, D-083 continuam abertas, com dono reatribuído para S17/S18
   (nenhuma delas bloqueia o dashboard, a auditoria, as denúncias ou o arquivamento).

## Global Constraints
- TypeScript strict, sem `any`; Zod em toda fronteira (formulários, Server Actions).
- Componente React ≤ 250 linhas; Server Components por padrão; `"use client"` só com interação (formulários).
- Migration `0604_admin_reports.sql`: `uuid`/`created_at`/`updated_at`, RLS em toda tabela nova, toda função nova
  (inclusive gatilho) `SECURITY DEFINER` com `search_path = ''` e `REVOKE EXECUTE` explícito de
  `public, anon, authenticated, service_role` antes de qualquer `GRANT`, gatilhos `enable always` nas trocas de
  estado/auditoria, grants por coluna. Teste de banco cobrindo `has_function_privilege` para cada função nova.
- Nunca inventar número no dashboard: toda contagem é uma consulta real; falha vira "indisponível" por categoria.
- `getSessionActor` + verificação de papel em toda Server Action; a tabela `students` nunca é lida pelo admin.

## Review Focus
- RLS de `reports`: denunciante só insere a própria denúncia já `open`/sem resolução; só admin/system leem e
  resolvem; transição de estado (`open -> reviewing/resolved/dismissed`, `reviewing -> resolved/dismissed`) só pelo
  gatilho de guarda, nunca “resolvido -> aberto” de novo.
- `resolution_note`/`detail_code`: regex de código, nunca aceitam espaço (bloqueia prosa/PII por construção).
- `admin_ai_settings` (Server Action): Zod espelha os CHECKs da 0202; `auto_publish_enabled` e `routes` nunca no
  payload aceito pelo schema (mesmo que alguém injete no formulário, o Zod strip/reject).
- `list_archive`: só a partir de `published`; motivo obrigatório, ≤ 1000 chars (CHECK já existente).
