# S24 · Portal B2B: cadastro, chaves e API v1 · Plano de implementação (trilha B2B, faixa 05xx)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Parceiros B2B dos tipos **varejista**, **marca** e **EdTech/ERP** se cadastram em `/parceiros` (B2B00), aceitam os termos da API e aguardam **aprovação do admin** (Admin15). Aprovados, entram no portal `/b2b` (B2B01 visão, B2B02 chaves, B2B03 documentação) e emitem chaves `x-listacerta-key` por ambiente (`test` = sandbox com dados de demonstração, `live` = produção), **mostradas uma única vez**, guardadas só como **HMAC-SHA256 com pepper de servidor**, com **escopos**, **revogação imediata** e **rotação sem downtime** (duas chaves ativas ao mesmo tempo). API REST versionada `/v1` com os endpoints do PLAN e do SPEC-2: `GET /v1/schools`, `GET /v1/schools/{inep}`, `GET /v1/schools/{inep}/lists`, `GET /v1/lists/{id}`, `GET /v1/lists/{id}/items`, `POST /v1/carts/match`. A API expõe **só listas públicas e dados agregados**. **Rate limit por chave** (por minuto e por dia) em Postgres atômico, com `429` + `Retry-After`. Documentação navegável gerada **do mesmo contrato Zod** dos endpoints. Aceite do PLAN: **nenhuma rota devolve dado pessoal, com teste**; **chave revogada falha na hora**.

**Architecture:** Fonte de verdade no banco (`0501_b2b_partners_api.sql`): tabelas `b2b_partners`, `b2b_partner_members`, `b2b_partner_events` (imutável), `b2b_api_keys`, `b2b_rate_windows`, `b2b_usage_daily`, e funções `SECURITY DEFINER` que são a **única** porta de escrita e a **única** leitura da API (`b2b_v1_*`, que codificam explicitamente a regra pública: lista `published` com versão atual, escola não suspensa de município habilitado, `is_demo` por ambiente, cobertura por UF). O app não guarda estado: cada requisição `/v1` faz **lookup da chave sem cache** → comparação HMAC em tempo constante no Node (`crypto.timingSafeEqual`) → consumo atômico do limite (que **revalida a chave** na mesma transação) → leitura por função → **validação da resposta por esquema Zod `.strict()`** (campo fora do contrato quebra a resposta em vez de vazar) → uso agregado gravado depois da resposta (`after()`). Contrato único em `features/b2b/api/contract.ts` (registro de endpoints com esquemas de path/query/body/resposta, escopo, erros e exemplos) alimenta os Route Handlers, o `openapi.json` e a página B2B03. Portal e admin seguem o padrão da S13/S14: leitura por RLS + grants por coluna (sem `key_hash`), escrita pelo servidor com `SessionActor` chamando as funções. **Sem chamada de IA.**

**Tech Stack:** Next.js 16 (Route Handlers em `app/v1/**`, `after()` de `next/server`, runtime Node), TypeScript strict, Zod 4 (`z.toJSONSchema` nativo, **sem dependência nova**), `node:crypto` (HMAC, `randomBytes`, `timingSafeEqual`), Supabase (RLS, funções SECURITY DEFINER), Vitest, agent-browser + `curl`. **Worktree de implementação:** decidido pelo orquestrador; recomendado `../listaescolar-wt/T5-b2b` com `.track` = 5 (índice B2B do `supabase/README.md`; app em `PORT=3005`), porque o T1 hospeda a S21 em paralelo (Ruling). Sessões agent-browser `t5s24-*`; **nunca `pkill`**; encerrar só o servidor da própria porta (`kill "$(lsof -ti tcp:3005 -sTCP:LISTEN)"`).

## Global Constraints

### Exposição de dados (regra dura; aceite do PLAN)
- **Só listas públicas:** uma lista sai pela API **se e somente se** `school_lists.status = 'published'`, `current_version_id` não nulo, versão atual `status = 'published'`, escola com `verification_status <> 'suspended'`, município `is_enabled`. Só a **versão atual** é exposta (sem histórico de versões `superseded`, Ruling). Uma escola sai se o município está habilitado e ela não está suspensa (cadastro INEP aparece como `verified: false`; **INEP não é verificação**).
- **`is_demo` explícito por ambiente:** chave `live` → só linhas com `schools.is_demo = false` **e** `school_lists.is_demo = false`; chave `test` (sandbox, "dados de amostra" do SPEC-2) → só linhas demonstrativas (`schools.is_demo = true` **ou** `school_lists.is_demo = true`). Sem dado de demonstração no banco, o sandbox devolve vazio (nada inventado). Toda resposta leva `meta.environment` e cada objeto de escola/lista leva `is_demo`.
- **Cobertura por UF:** parceiro com `coverage_ufs` (plano Regional) só vê escolas/listas desses UFs; `null` = nacional. Fora da cobertura = `404` igual a inexistente.
- **Whitelist por endpoint (colunas permitidas, nada além):** escola = `inep`, `name`, `network`, `neighborhood`, `municipality { ibge_code, name, uf }`, `verified` (`verification_status = 'verified'`), `published_lists_count` (agregado), `is_demo`; lista = `id` (`school_lists.id`), `school_inep`, `grade { slug, name, stage }`, `school_year`, `version` (número), `published_at`, `item_count`, `is_demo`; item = `position`, `name` (`original_name`), `normalized_name`, `category`, `quantity`, `unit`. **Proibido em qualquer resposta:** dado de família ou aluno, `email`/`phone`/`address`/`cep` de escola, ids de perfil (`created_by`, `approved_by`, `submitted_by`, `profile_id`, `actor_id`, `requester_id`, `owner_id`), campos internos (`alerts`, `confidence`, `source`, `submission_id`, `publication_key`, `publication_hash`, `registry_source`, `source_batch_id`, `current_version_id`, ids de versão/item), dados de carrinho, lead, papelaria, cópia de pai, `ai_decisions`, `audit_log`, `consents`, e qualquer dado de outro parceiro.
- **Defesa em profundidade:** (1) as funções `b2b_v1_*` devolvem só colunas da whitelist; (2) cada Route Handler passa a saída por `responseSchema.strict().parse()` do contrato (campo extra = `500 internal_error` registrado, nunca vazado); (3) **teste de varredura de TODAS as respostas** (Task 2): percorre o registro de endpoints (e um teste de completude garante que todo arquivo `app/v1/**/route.ts` está no registro), chama cada rota contra o banco real semeado com dados sensíveis (e-mail/telefone/endereço de escola, perfis com nome, `alerts`/`confidence`, envio com `submission_id`, cópia de pai com nome de aluno no item, lead com código, papelaria, dados de outro parceiro, lista não publicada, escola suspensa, município desabilitado, demo × real) e varre recursivamente cada corpo (inclusive erros `4xx/5xx` e `openapi.json`) por **chaves proibidas** (lista fixa acima + regex `/(e-?mail|phone|telefone|cpf|address|endereco|cep|profile|user_id|actor|requester|owner|created_by|approved_by|submitted_by|alerts?|confidence|submission|publication_|source)/i`, com allowlist explícita e mínima só para as chaves do contrato) e por **valores proibidos** (as strings e UUIDs semeados: e-mails, telefones, CPF, UUIDs de perfis/envio/versão/item/papelaria/lead, nome do aluno, apelido, código `LC-`); também regex de e-mail, CPF e telefone brasileiro sobre o JSON inteiro.
- **`POST /v1/carts/match`:** entrada `{ list_id, skus: [{ sku, name }] }` (1..5000 SKUs; `sku` 1..64 caracteres `[A-Za-z0-9._:/-]`; `name` 1..200; corpo ≤ 1 MB, `content-type: application/json`); casa **só com os itens da lista pública** (mesma regra de exposição) por algoritmo determinístico sem IA: chave exata (`normalizeItemKey` da S12) → senão conjunto de tokens (todos os tokens significativos do item, ≥ 2 caracteres e fora de uma lista fixa de conectivos, presentes no nome do SKU; empate = menor nome, depois ordem de entrada). Resposta: `{ list_id, version, matched, unmatched, items: [{ position, name, quantity, unit, match: { sku, method: 'exact' | 'tokens' } | null }] }`. **Sem dado de usuário, sem preço, sem `cart_url`** (o link para o carrinho do parceiro é do widget, S25; Ruling), **sem persistir o catálogo do parceiro** (só contagens agregadas de itens casados/total no uso diário). Não ecoa SKUs que não casaram.

### Chaves (`x-listacerta-key`)
- **Formato:** `lc_<env>_<id>_<secret>` com `env ∈ {live, test}`, `id` = 12 caracteres Crockford base32 aleatórios (identificador público, único) e `secret` = 32 bytes de `randomBytes` em base64url (43 caracteres). Mostrado **uma única vez** (retorno da Server Action para um componente cliente que exibe, copia e descarta; nunca em URL, cookie, flash, log, banco ou `audit_log`); a tela avisa "Copie agora: esta chave não será mostrada de novo".
- **Armazenamento:** só `key_hash = HMAC-SHA256(B2B_API_KEY_PEPPER, secret)` em hex (64), `hash_version` (para rotação futura do pepper), `public_id`, `last4` (últimos 4 do `secret`) e ambiente. Pepper **só** no servidor: `B2B_API_KEY_PEPPER` (≥ 32 caracteres) opcional em `lib/env.ts`, nome e comentário em `.env.example`; sem pepper → API `503 service_unavailable` e o portal mostra "Emissão de chaves indisponível no momento". O pepper nunca vai ao banco (o hash é calculado no Node). Exibição mascarada: `lc_live_••••••••••••7f2a`.
- **Verificação:** cabeçalho ausente/malformado → `401 invalid_key` sem consultar o banco; `id` → `b2b_key_lookup(public_id)` (somente leitura, **sem cache**) → `timingSafeEqual` entre o HMAC calculado e o `key_hash` (buffers de mesmo tamanho; `id` inexistente compara com um hash fixo de mesmo tamanho para não diferenciar tempo) → chave utilizável = `status = 'active'` e (`expires_at` nulo ou `> now()`) e parceiro em estado que permite o ambiente (`test`: `sandbox|active`; `live`: `active`). Toda falha de chave (ausente, malformada, inexistente, hash errado, revogada, expirada, parceiro suspenso) devolve **o mesmo** `401 invalid_key` com `WWW-Authenticate: ListaCerta-Key`. Chave só no cabeçalho (query string ignorada).
- **Revogação imediata:** não existe cache de validade; além disso `b2b_rate_consume` **revalida a chave dentro da mesma transação** do consumo, então uma revogação confirmada entre o lookup e o consumo também falha (`401`). Revogar = `status = 'revoked'`, `revoked_at`, `revoked_by`, `revoke_reason`; irreversível.
- **Rotação sem downtime:** "Rotacionar" cria uma chave nova (mesmo ambiente e escopos) e marca a antiga com `expires_at = now() + carência` escolhida no diálogo (1, 7 ou 30 dias; padrão 7; Ruling), na mesma transação. No máximo **duas chaves utilizáveis por (parceiro, ambiente)** (atual + anterior): terceira → `too_many_keys` (revogue uma antes). Durante a carência as duas autenticam; depois dela a antiga falha com `401` sem job algum (a expiração é checada no lookup).
- **Escopos:** `schools:read`, `lists:read`, `carts:match`. Permitidos por tipo (espelho SQL `b2b_allowed_scopes(type)` × TS `ALLOWED_SCOPES`, com teste de contrato): varejista = os três; marca = `schools:read`, `lists:read`; EdTech/ERP = `schools:read`, `lists:read` (publicar lista pela API não está no PLAN; Ruling). Chave sem o escopo do endpoint → `403 insufficient_scope`.
- **Suspensão do parceiro** (Admin15: "Suspender uma conta revoga as chaves na hora") revoga **todas** as chaves na mesma transação (`revoke_reason = 'partner_suspended'`); reativar não ressuscita chaves (o parceiro emite novas). Rebaixar `active → sandbox` revoga as chaves `live`.

### Rate limit por chave (decisão justificada)
- **Armazenamento: Postgres, janela fixa, atômico.** Rejeitados: memória do processo (Vercel serverless tem várias instâncias efêmeras: o limite seria por instância e zeraria a cada cold start) e Redis/Upstash (serviço novo, conta e credencial = pendência humana e possível custo; fora das exceções do CLAUDE.md sem necessidade). O custo é uma chamada RPC a mais por requisição, aceitável no volume do piloto (Ruling; revisitar com carga real).
- **Unidade:** o limite é identificado pela chave e contado no **balde (parceiro, ambiente)**, para a rotação (duas chaves) não dobrar a cota do plano (Ruling). Limites por minuto e por dia vêm da linha do parceiro (`live_rate_per_minute`, `live_rate_per_day`, `test_rate_per_minute`, `test_rate_per_day`), **definidos pelo admin na aprovação** (nenhum número de limite no código além das faixas de validação em `features/b2b/limits.ts`, espelhadas no SQL). Dia no fuso America/Cuiaba.
- **`b2b_rate_consume(p_key_id)`:** `pg_advisory_xact_lock` por (parceiro, ambiente) → revalida a chave → lê/incrementa as janelas `minute` e `day` em `b2b_rate_windows` só se ambas estiverem abaixo do limite (negada não consome) → devolve `{ allowed, limit, remaining, reset_at, window }` da janela mais restritiva. Teste de concorrência: N requisições paralelas com limite K → exatamente K permitidas.
- **Respostas:** toda resposta autenticada leva `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (epoch em segundos) da janela mais restritiva; `429 rate_limited` com `Retry-After` (segundos até o fim da janela) e corpo padrão, **sem** revelar outro parceiro, contagem de outros baldes nem detalhe interno.
- **Limpeza:** `b2b_prune_rate_windows(p_older_than interval default '2 days')` chamado por `GET /api/cron/b2b-maintenance` (`Authorization: Bearer ${CRON_SECRET}`, comparação em tempo constante, sem segredo → 503; reusar `features/leads/cron-auth.ts` se servir, só domínio puro), agendado diário em `vercel.json`.
- Chave inválida não consome cota de ninguém (o limite só roda depois do HMAC válido). Flood de chaves inválidas por IP fica para a S19 (D-001; Ruling: a S19 inclui `/v1` no limite por IP); a entropia de 256 bits torna força bruta inviável.

### Uso e auditoria
- **Uso agregado sem IP nem PII:** `b2b_usage_daily` por (chave, dia America/Cuiaba, endpoint do registro, classe de status `2xx|4xx|429|5xx`) com `request_count` e, para `carts.match`, `match_items_total`/`match_items_matched`. Nenhum IP, user agent, corpo, query, SKU ou parâmetro. Gravado por `b2b_usage_record(...)` depois da resposta (`after()`); falha de gravação nunca muda a resposta. Requisições com chave inválida não são atribuídas a ninguém (não gravadas).
- **Auditoria administrativa:** `audit_row_change` `enable always` em `b2b_partners` (sem `contact_name`), `b2b_partner_members` e `b2b_api_keys` (sem `key_hash`); `b2b_partner_events` imutável (UPDATE/DELETE/TRUNCATE bloqueados, `enable always`).
- Logs do servidor: só `request_id`, `public_id` da chave, código de erro e endpoint; nunca o cabeçalho da chave, corpo ou SKU.

### Contrato HTTP da API
- **Versionamento:** prefixo `/v1`; mudança incompatível = `/v2`; `meta.api_version = "v1"`. Política escrita na documentação.
- **Envelope:** sucesso `{ data, next_cursor?, meta: { api_version, environment, request_id } }`; erro `{ error: { code, message, request_id, details? } }` com `code ∈ { invalid_key, insufficient_scope, not_found, invalid_request, payload_too_large, unsupported_media_type, method_not_allowed, rate_limited, service_unavailable, internal_error }`; `details` só com `path` e código da issue do Zod (nunca o valor recebido). **Nunca stack, SQL, mensagem do Postgres, hint ou nome de tabela.** Mensagens em português fixas por código.
- **Paginação:** keyset com cursor opaco (base64url de JSON validado por Zod); `limit` padrão 50, máximo 100 (escolas, listas) e padrão 200, máximo 500 (itens); `next_cursor` ausente na última página. Ordem estável: escolas por (`normalized_name`, `inep`), listas por (`school_year desc`, `grade.sort_order`, `id`), itens por `position`.
- **Filtros:** `GET /v1/schools?city=<ibge 7 dígitos>&uf=<UF>&q=<texto 2..80>&has_lists=<bool>&limit&cursor` (`q` usa `search_normalize` da 0102); `GET /v1/schools/{inep}/lists?year=<2020..2100>`; `inep` `^[0-9]{8}$`; `id` UUID. Parâmetro desconhecido → `400 invalid_request` (query `.strict()`).
- **Cache-control:** `Cache-Control: no-store` em tudo (resposta autenticada, contada por chave e sujeita a revogação imediata), `X-Content-Type-Options: nosniff`, `Content-Type: application/json; charset=utf-8`, `X-Request-Id`. `GET /v1/openapi.json` é público (sem chave, sem dado), `Cache-Control: public, max-age=300`.
- **CORS:** nenhum cabeçalho `Access-Control-*` (API servidor-a-servidor; chave secreta nunca vai ao navegador; o uso embutido em sites é o widget da S25). Métodos não declarados → `405` com `Allow`.
- **Rotas fora do proxy de sessão:** `proxy.ts` exclui `v1/` do matcher (sem cookie, sem refresh de sessão, sem redirect de login); `/v1` e `/b2b` com `noindex` e bloqueados no `robots.ts`.
- **Tempo:** timeout de 8 s por requisição ao banco (AbortSignal) → `503`; dados sem fonte = campo `null` ou omitido conforme o esquema, nunca estimado.

### Parceiros, papel e portal
- **Papel:** **sem valor novo no enum `user_role`** (Ruling). Acesso ao portal = linha em `b2b_partner_members` (tabela de membros, padrão `stationery_members`), independente de `profiles.role`: o mesmo perfil pode ser responsável (`parent`) e parceiro. Motivos: `alter type ... add value` não pode ser usado na mesma transação da migration, mudaria `UserRole`/`access.ts` e todas as matrizes das trilhas paralelas (S21), e promover papel (como a S13 faz com `stationery_member`) tiraria o acesso de pai. `/b2b` entra em `ProtectedPrefix` para `parent`, `school_member`, `stationery_member` e `admin` (nunca `system`); o layout de `/b2b` exige membro (senão redireciona para `/parceiros?cadastro=1`); admin vê o portal só pelo Admin15.
