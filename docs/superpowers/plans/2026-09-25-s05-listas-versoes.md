# S05 · Listas oficiais e versões · Plano de implementação (trilha Dados, índice 1)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Tabelas `grades`, `school_lists`, `list_versions`, `list_items`. O perfil da escola exibe **só a versão `published` atual**; o histórico mostra as anteriores com o rótulo "versão anterior"; uma lista arquivada nunca aparece como atual. Máquina de estados da lista em `features/lists/state.ts`, com testes de todas as transições válidas e inválidas (as proibidas lançam erro), espelhada no banco por funções que aplicam a mesma matriz.

**Architecture:** Migration `0103`: `grades` (semeada com os slugs do catálogo estático da S04), `school_lists` (escola × série × ano letivo, estado `list_status`, ponteiro para a versão atual), `list_versions` (versões numeradas, com estado próprio), `list_items`, `list_status_events` (trilha imutável). Transições e publicação por funções SQL `SECURITY DEFINER` só `service_role` (`list_transition`, `list_publish_version`, `list_archive`) que aplicam a matriz, travam a linha e gravam eventos. Domínio em `features/lists/` (matriz TS idêntica à do banco e comparada por teste contra o RPC real, repositório server-only, consultas públicas com o cliente publicável). Páginas públicas mostram apenas o que a RLS permite. **Sem FK para tabelas de outras trilhas** (ADR-004): `submission_id` de uma versão é `uuid` solto (Pipeline). Quem chama a publicação a partir da revisão é a porta `ListPublisher` da S09/S11.

**Tech Stack:** Next.js 16, Zod, Supabase (RLS, funções SECURITY DEFINER), Vitest, agent-browser. Worktree `../listaescolar-wt/T1-dados`, trilha 1 (`.track` = 1): `pnpm db:start`, `pnpm db:env`, app em `PORT=3001`. **Nome de sessão único no agent-browser; nunca `pkill -f agent-browser`.**

**Spec:** `docs/SPEC.md` §4 (`list_status`; "publicada exige escola, série, ano letivo e versão"; "arquivada nunca aparece como a versão atual"; "listas enviadas começam como candidatas e nunca aparecem como oficiais"), §5 (Séries e listas), §8; `docs/PLAN.md` S05; ADR-004. Telas (leia PNG e HTML em `docs/design`): `App05-Lista` (mobile 390×844, `/escolas/[inep]/[serie]`), `Escola07-NovaLista` e `Escola10-ListaDetalhe` (desktop; fluxo de administração da escola: **adiado** para depois da S06, que cria o vínculo escola↔administrador, e da S10; registre Ruling).

## Global Constraints
- Migration `supabase/migrations/0103_lists_and_versions.sql` (faixa Dados 01xx). Toda tabela: `id uuid primary key default gen_random_uuid()`, `created_at`, `updated_at` (trigger `set_updated_at`), RLS habilitada; FK só para `schools`, `municipalities`, `profiles`, `auth.users` e tabelas desta migration.
- `grades`: `slug text unique` (semear **exatamente** os 16 slugs de `features/grades/catalog.ts`: `ei-maternal-1`, `ei-maternal-2`, `ei-pre-1`, `ei-pre-2`, `ef-1`…`ef-9`, `em-1`…`em-3`), `name`, `stage` enum `grade_stage` (`ei`,`ef`,`em`), `sort_order`. Um teste garante que a tabela e o catálogo TS têm os mesmos slugs e ordem.
- `school_lists`: `school_id` → schools (on delete restrict), `grade_id` → grades, `school_year int check (school_year between 2020 and 2100)`, `status list_status not null default 'draft'`, `current_version_id uuid` (FK deferrable para `list_versions`), `published_at`, `archived_at`, `is_demo bool`, `unique (school_id, grade_id, school_year)`. **Publicada exige** escola, série, ano e versão atual (check: `status <> 'published' or current_version_id is not null`).
- `list_versions`: `list_id` → school_lists (cascade restrito por FK; sem delete direto), `version_number int` (sequencial por lista, `unique(list_id, version_number)`), `status version_status` (`candidate`, `published`, `superseded`, `archived`), `source` enum (`school_upload`, `parent_upload`, `admin`), `submission_id uuid` (sem FK), `published_at`, `archived_at`, `created_by` → profiles nullable, `item_count int`. **No máximo uma versão `published` por lista** (índice único parcial). `list_items`: `version_id`, `position int`, `original_name`, `normalized_name`, `category text`, `quantity numeric(10,2) check (> 0)` nulo permitido, `unit text`, `confidence numeric(4,3) between 0 and 1`, `alerts jsonb` (array; códigos do spec §6: `low_confidence_item`, `ambiguous_item`, `handwritten`, `possible_collective_item`, `restrictive_brand_or_spec`, `text_document_mismatch`, `invalid_school_grade_year`; check de array e tamanho), `unique(version_id, position)`. Itens de versão `published/superseded/archived` são **imutáveis** (trigger: só versão `candidate` aceita insert/update/delete de itens).
- Enum `version_status` e matriz do estado da lista (`list_status`, enum existente): `draft→submitted`; `submitted→processing`; `processing→processing_async|review_needed|human_review|approved|rejected`; `processing_async→processing|review_needed|human_review|approved|rejected`; `review_needed→human_review|approved|rejected`; `human_review→approved|rejected`; `approved→published`; `published→archived`; `rejected→draft` (reenvio); `archived` terminal. Qualquer outra transição (incluindo para o mesmo estado e origem/destino inexistentes) é erro em TS (`InvalidListTransitionError`) e no banco (errcode `23514` com mensagem estável). Matriz completa 10×10 testada (100 pares) contra o RPC real. **Ator não define a matriz na S05** (S09/S10 decidem quem chama); a função grava o ator no evento e exige `p_actor_id` não nulo para `approved`, `published` e `rejected`.
- `list_publish_version(p_list_id, p_version_id, p_actor_id)`: só quando a lista está `approved` e a versão é `candidate` da própria lista; marca a versão como `published`, a anterior `published` como `superseded`, define `current_version_id`, `published_at`, e a lista vai a `published` (numa transação, lock da linha `for no key update`). `list_archive(p_list_id, p_actor_id, p_reason)`: `published→archived`; todas as versões da lista viram `archived`; a lista deixa de ter versão atual (`current_version_id = null`, permitido quando `status = 'archived'`). Reenviar uma lista `published` cria nova versão `candidate` (a lista permanece `published` com a versão atual antiga visível até a nova ser publicada) — a nova versão é criada por `list_create_candidate_version(p_list_id, p_source, p_submission_id, p_created_by)` (service_role), que devolve o `version_id` e o número seguinte. Lista `draft/submitted/processing*/review_needed/human_review/approved/rejected` **nunca é pública**.
- RLS (público = `anon` + `authenticated`): `school_lists` visíveis só com `status = 'published'`, escola de município habilitado; `list_versions` visíveis quando `status in ('published','superseded')` e a lista está `published`; `list_items` idem, pela versão; `grades` públicas. Admin/system leem tudo; ninguém escreve pelo PostgREST (escrita só via funções/`service_role`). `list_status_events`: só admin/system leem. Um teste prova que uma lista `archived`, `approved` ou `rejected` e uma versão `candidate` não vazam pelo público, e que a versão `superseded` só aparece com a lista `published`.
- **Nunca inventar:** se não há lista publicada, a UI mostra "lista não publicada" (indisponível); nada de itens de exemplo; dados demonstrativos com `is_demo = true` e selo "Demonstração". O público **não vê** alertas de revisão (`alerts`) nem `confidence`: são internos (sinalizações para revisão, não parecer jurídico). Nenhum dado de menor.
- Domínio (`features/lists/`): `state.ts` (`LIST_TRANSITIONS`, `canTransition`, `assertTransition`, `InvalidListTransitionError`), `schemas.ts` (Zod das linhas do RPC e dos itens), `repository.ts` (server-only; leitura pública com cliente publicável, escrita com service role), `queries.ts`. A matriz TS e a do banco são comparadas por teste (Task 2). Ruling: a matriz vive uma vez em TS e uma vez em SQL, com o teste como fiador.
- UI: `/escolas/[inep]/[serie]?ano=` (App05-Lista): itens agrupados por categoria (se houver), quantidade e unidade, indicação da versão atual (número e data de publicação), histórico com "versão anterior" (só publicada/superseded), estados: lista não publicada, erro (retry), 404 (INEP/série inválidos), demonstração. O perfil `/escolas/[inep]` (S04) passa a apontar o seletor de série/ano para essa página e mostra o estado real (publicada ou não) — o bloco "lista não publicada" só quando de fato não existe. Sem CTA de envio até a S11. `noindex` enquanto a lista for de demonstração; lista publicada de escola `claimed|verified` indexável (regras da S04).
- Script `pnpm seed:demo-lists` (local/staging, `is_demo = true`, recusa alvo que não seja loopback ou o ref de staging, como `pnpm import:inep`): cria listas de demonstração com itens fictícios rotulados para as escolas demo; usado no E2E. **Nunca** cria lista real.
- Segurança/qualidade: Zod em toda fronteira; service role só server-only; componentes ≤250 linhas; `"use client"` só com interação; TypeScript strict sem `any`; migration no padrão (search_path vazio, revoke execute explícito, um comentário por política). Ledger: Rulings desta trilha em `docs/superpowers/ledger-dados.md`.

## Review Focus
- Vazamento: lista/versão não publicada (candidate, approved, human_review, rejected, archived) visível ao público por qualquer rota/rpc/join; versão superseded de lista arquivada; itens de versão `candidate`; alertas/confiança no HTML público ou na resposta da API pública.
- Máquina de estados: pares fora da matriz aceitos; corrida entre duas transições/publicações (lock, dupla publicação); publicar versão de outra lista; publicar sem aprovar; duas versões `published`; `archived` reabrindo; itens mutáveis depois de publicados.
- `current_version_id` inconsistente (aponta para versão de outra lista, para versão não publicada, ou existe em lista não publicada); reenvio de lista publicada mantendo a versão antiga visível até a troca.
- Integridade: unicidade (escola, série, ano); série inexistente; ano fora do intervalo; `version_number` sob concorrência; deleção de escola com listas (restrict).
- Estados de UI: nenhum item inventado; erro do banco sem vazar mensagem; 404 indistinguível entre "escola/série inexistente" e "sem lista".
